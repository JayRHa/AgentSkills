# Outcome vs Output: The Heart of Good OKRs

The single most common OKR mistake is writing **outputs** (things you do) where **outcomes** (changes that result) belong. Key Results must measure outcomes.

## Definitions

| Term | Question it answers | Example | Belongs as |
|------|--------------------|---------|------------|
| Output | What did we produce/do? | "Shipped the new checkout" | Initiative |
| Outcome | What changed as a result? | "Cart abandonment dropped from 68% to 50%" | Key Result |
| Impact | What's the long-term value? | "Revenue per visitor up" | Objective theme / North Star |

## The "So That" Ladder

When a user gives you an output, ladder up to the outcome by repeatedly asking **"so that what happens?"** until you reach something measurable about a person, the business, or the world.

Example:

1. "Rebuild the onboarding flow" — *so that?*
2. "...new users understand the product faster" — *so that? (how would we see it?)*
3. "...more of them complete setup" — measurable: **activation rate**
4. "...and more of them stay" — measurable: **week-4 retention**

Stop laddering when you have a metric you can put a baseline and target on. That metric is your Key Result.

## The Inversion Test

For any candidate Key Result, ask: **"Could we complete this perfectly and still fail the objective?"**

- "Launch the referral program" — Yes, we could launch it and get zero referrals. ➜ Output. Demote.
- "Drive 20% of new signups through referrals" — No; if we hit it, the objective moved. ➜ Outcome. Keep.

## Output → Outcome Lookup Table

| Output (what teams write) | Underlying outcome (what to measure) |
|---------------------------|--------------------------------------|
| Ship feature X | Adoption of feature X (% of active users using it weekly) |
| Run 3 marketing campaigns | Qualified leads generated; cost per acquisition |
| Redesign the website | Conversion rate; bounce rate; time-to-value |
| Hire 5 engineers | Throughput / cycle time / on-time delivery enabled by capacity |
| Write documentation | Self-serve ticket deflection rate; time-to-first-success |
| Migrate to new infrastructure | p95 latency; uptime; infra cost per request |
| Launch mobile app | Share of MAU on mobile; mobile retention |
| Hold weekly trainings | Skill assessment pass rate; ramp time for new hires |
| Implement a CRM | Sales cycle length; forecast accuracy; rep productivity |
| Create a customer council | NPS; logo retention; expansion revenue |
| Reduce tech debt / refactor | Change failure rate; deploy frequency; incident MTTR |
| Build a dashboard | Decisions changed / time-to-insight (measurable usage + action) |

## When an Output Is Acceptable

Use a **binary milestone** key result only when the deliverable itself is the externally-verified value and intermediate progress is meaningless:

- "Achieve SOC 2 Type II certification by Q3."
- "Obtain FDA 510(k) clearance for device."

Even then, prefer a graded version when possible (e.g., "Close 18 of 22 SOC 2 controls"). Limit binary KRs to at most one per objective.
