# NIST SP 800-63B — Quick Reference for Authentication Policy

This condenses the operative requirements of NIST Special Publication 800-63B
(Digital Identity Guidelines — Authentication and Lifecycle Management) into an
actionable checklist. It is a working summary, not a substitute for the publication.

## 1. Authenticator Assurance Levels (AAL)

| Level | Requirement | Typical use |
|-------|-------------|-------------|
| AAL1 | Single-factor OR multi-factor; some assurance the claimant controls an authenticator | Low-risk consumer accounts |
| AAL2 | Two distinct authentication factors (proof of possession + something you know/are) | PII, financial, account data |
| AAL3 | Hardware-based authenticator + phishing-resistant verifier; cryptographic proof | Admin, privileged, regulated |

The three authentication factors:
- Something you know (password / memorized secret)
- Something you have (phone, security key, token)
- Something you are (biometric — only as part of MFA, never sole factor)

Selecting a level: classify the impact of an account compromise (confidentiality,
integrity, financial, safety, reputation). Map higher impact to higher AAL. When in
doubt for systems holding personal data, default to AAL2.

## 2. Memorized Secrets (passwords) — the rules

MUST:
- Allow a minimum length of at least 8 characters (recommend enforcing 12+).
- Allow at least 64 characters maximum length.
- Accept all printable ASCII characters, the space character, and Unicode.
  Count each Unicode code point as at least one character.
- Compare the prospective secret against a blocklist of compromised/common values
  and reject matches (breached corpora, dictionary words, repetitive/sequential
  characters, and context-specific words such as the service name or username).
- Provide a reason and allow the user to choose a different value on rejection.
- Hash and salt memorized secrets using a suitable one-way KDF (see password-storage.md).
- Allow paste functionality in the entry field.
- Offer an option to display the secret as it is typed ("show password").
- Limit the number of failed authentication attempts (rate limiting / throttling).

MUST NOT:
- Impose composition rules (e.g. require mixtures of character types).
- Require periodic (e.g. 60/90-day) rotation without evidence of compromise.
- Permit the use of password hints accessible to unauthenticated users.
- Prompt knowledge-based authentication / "security questions" as a factor.
- Truncate the secret for processing.

Force a change ONLY when there is evidence the authenticator was compromised.

## 3. Rate limiting & throttling

- Limit consecutive failed attempts on a single account (NIST: no more than 100
  failures per account before additional defenses).
- Apply per-IP and per-account throttling with exponential backoff.
- Use CAPTCHA, delays, or step-up after a threshold rather than permanent lockout.
- Avoid permanent account lockout (denial-of-service risk); prefer time-boxed soft lock.

## 4. Multi-factor authentication

Preference order (most to least phishing-resistant):
1. FIDO2 / WebAuthn security keys and passkeys (phishing-resistant) — required for AAL3.
2. Authenticator apps generating OTP (TOTP).
3. Push-based approval (with number matching to resist fatigue attacks).
4. SMS / phone OTP — "restricted" by NIST; acceptable only as last resort, never for
   privileged or high-value accounts (SIM-swap and SS7 interception risk).

Biometrics are only usable as part of MFA bound to a specific device, never standalone.

## 5. Session management

- Reauthentication: AAL2 at least every 12 hours or after 30 minutes inactivity;
  AAL3 at least every 12 hours or after 15 minutes inactivity.
- Bind session secrets to the user agent; regenerate session IDs on privilege change.
- Invalidate all sessions on password change/reset and on logout.

## 6. Account recovery

- Use single-use, time-limited, high-entropy reset tokens via an out-of-band channel.
- Do not use security questions for recovery.
- Re-verify identity proportionate to AAL before allowing recovery.
- Rate-limit reset requests; avoid disclosing whether an account exists.

## 7. Verifier-impersonation & general verifier requirements

- Establish a protected channel (TLS) for all credential transmission.
- Do not store the secret in a reversible form; store the KDF output only.
- Consider a secret salt value ("pepper") held separately from the database.
- Do not log the secret. Log authentication events (without secrets) for detection.

## 8. Engineering acceptance checklist

- [ ] Min length enforced (>=8, recommend 12); max >=64 accepted, no truncation.
- [ ] All printable + Unicode + space accepted.
- [ ] No composition rules enforced.
- [ ] No mandatory periodic rotation.
- [ ] Breach/blocklist screening on create and change.
- [ ] Argon2id (or approved KDF) with tuned parameters; per-user salt; optional pepper.
- [ ] Paste allowed; show-password toggle available.
- [ ] Per-IP and per-account rate limiting with backoff; no permanent lockout.
- [ ] MFA required at AAL2+; phishing-resistant option offered; no SMS for admin.
- [ ] Reset tokens single-use, time-limited, out-of-band; sessions invalidated on change.
- [ ] Generic error messages (no username/password distinction; no account enumeration).
- [ ] Auth events logged without secrets; change notifications emailed.
